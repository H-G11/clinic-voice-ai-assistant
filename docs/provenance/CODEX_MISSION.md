Задание для Codex: Голосовой ассистент регистратуры — доведение MVP до чекпоинта
Ты — ведущий инженер и тестировщик. Работай не в новом проекте, а в текущем локальном репозитории пользователя на Windows. Времени мало, работает один человек. Нужен рабочий, воспроизводимый сквозной результат, а не технологическая витрина. Не задавай несущественных вопросов: инспектируй файлы, принимай разумные решения и исполняй. Если чего-то объективно недостаёт (OpenAPI, Excel, права на тестовые операции), чётко фиксируй блокер и продолжай независимые задачи.
Исходное состояние (проверь по реальным файлам)
Ожидается MVP v2, Python 3.11+, Windows, RTX 4060 Laptop 8 ГБ, 16 ГБ RAM, микрофон и интернет. Файлы: app.py, core/{dialog,parse_ru,voice,mis,service,schedule,store}.py, tests/{test_mvp,test_russian}.py, docs/contracts.md, AGENTS.md, start_windows.bat. Текстовая запись в MockMIS/SQLite работает; Whisper распознаёт примерно 80% обращений по субъективной оценке пользователя; реальный голосовой ответ пока не работает; диалог сухой. В app.py стоит запрет на MIS_MODE != mock; RealMIS в core/mis.py — заглушка, Excel синтетический. Точные API, schema Excel, тестовые пациенты и админка пока не подтверждены. Не называй mock настоящей МИС.
Неприкосновенные требования
1. Главный сценарий: голос или текст → намерение записи → врач/специальность → дата и свободный слот по расписанию → идентификация синтетического пациента → явное подтверждение → создание через тестовую МИС, когда появится API → голосовой ответ. При отсутствии API сохраняем корректно помеченное mock-демо.
2. Реальные персональные данные нельзя передавать внешним облачным ИИ. Не подключай облачные ASR, TTS, LLM. Никакой медицины: диагнозов, лекарств, рекомендаций. Медицинские вопросы, острая боль, жалобы, нестандартные вопросы и просьба оператора — безопасная передача/инструкция связаться с оператором; фактический перевод не симулируй как настоящий.
3. Генеративная модель не делает произвольных вызовов API. Все изменяющие операции — только через строгие проверяемые методы сервиса. Никакой записи без подтверждения; не озвучивать успех до подтверждённого результата МИС.
4. Лимит стенда: 10 API-запросов в минуту суммарно, включая чтение и повторные запросы. Кэшируй справочники; уважай 429/Retry-After. После сетевого таймаута на POST состояние uncertain: не повторяй POST вслепую, сначала сверка.
5. Не выполняй опасных системных команд, переустановку драйверов, массовые изменения системы, отправку файлов в сеть или тестовые мутации стенда без одобрения пользователя. Не выводи токены/секреты в терминал и логи. Работай в каталоге проекта, сначала сохрани возможность отката.
6. Сохрани и расширяй текущие интерфейсы, тесты и рабочую логику. Не меняй docs/contracts.md молча. .env, токены, базы с пациентами, .venv не коммить. Не создавай публичный шаринг Gradio; bind 127.0.0.1.
7. Технические ограничения: Windows и 16 ГБ RAM, избегай тяжёлых LLM/нескольких резидентных моделей. Выбирай локальные инструменты. Никакого Docker, Kubernetes, LangChain, RAG или масштабного переписывания.
Рабочий протокол — обязателен
Вначале: git status, краткий аудит ключевых файлов, затем baseline-тесты: .venv\Scripts\python.exe -m unittest discover -s tests -v (если есть .venv; иначе используй существующий Python без разрушения рабочего окружения). Зафиксируй baseline, ошибки и отсутствующие материалы в docs/progress.md; не притворяйся, что тесты прошли, если их не запускал. Работай малыми инкрементами. После каждого изменения повторно запускай тесты. Для каждого этапа отчитайся в 5 строках: что сделано, изменённые файлы, как проверить, тесты, что блокирует. Если репозиторий уже имеет коммиты, создавай осмысленные коммиты только с подтверждёнными изменениями; не пушь без согласия пользователя. Если репозиторий не инициализирован, попроси подтверждение или подготовь безопасный git init без затрагивания других проектов.
Этап A. Первые 10–15 минут: проверка и минимальный голосовой ответ
1. Осмотри app.py и core/voice.py. Проверь, почему при gr.Audio(..., autoplay=True) и установленном Windows SAPI пользователь не слышит голос. Учти, что tts_on по умолчанию False; проверь обработку возвращаемого аудиофайла и явное сообщение об ошибке вместо немого None.
2. Реализуй локальный реально слышимый TTS хотя бы одним способом. Самый быстрый вариант — Windows System.Speech при доступном русском голосе; добавь проверку доступных голосов, диагностику и fallback. Если русского голоса нет или SAPI нестабилен, подключай Piper с русским голосом только при возможности сделать это быстро и полностью локально. Не ломай основной поток, если голосовой движок недоступен: сообщи в UI, а текстовый сценарий пусть работает.
3. Критерий: после текстового ответа и включённого TTS в браузере появляется воспроизводимый WAV, после записи — голосовой результат. Проверку реального воспроизведения пользователь выполнит вручную; автоматические тесты должны только проверять путь сохранения аудиофайла и обработку ошибок.
4. Переходи дальше, если потратил ~15 минут и TTS завис на системной проблеме: документируй blocker, оставь текст и вернись позже.
Этап B. 20–35 минут: повысить надёжность распознавания и диалога
1. В core/voice.py измеряй отдельно latency ASR. Сохрани быстрый CPU fallback. Попробуй faster-whisper small на CPU/GPU только если быстро доступно. Для CUDA проверь совместимость ctranslate2, CUDA/cuDNN и текущих драйверов, не переустанавливай GPU-драйвер. Конфигурируемые переменные ASR_DEVICE, ASR_MODEL, параметры декодирования. av<19 уже важен для предотвращения ошибки metadata_errors. Не делай запуск MVP зависимым от загрузки большой модели.
2. Сгенерируй tests/asr_phrases.csv с 30–40 синтетическими русскими фразами: даты прописью, часы/половина десятого, специальности, исправления («нет, в понедельник»), явное «да/нет», ФИО, просьба оператора. Это набор для ручного прогона, НЕ выдавай его за уже измеренную точность ASR.
3. Исправь конкретные ошибки core/parse_ru.py и core/dialog.py на основе тестов: «в понедельник после обеда», «девять тридцать», «в два часа дня», «нет, в пятницу», «другое время», смена врача/даты, прошлые даты, несуществующие даты. Не выдумывай свободный слот, извлекай только из реального локального списка доступных слотов. При конфликте ASR или двусмысленном времени переспроси. Подтверждать вслух врач/дата/время/синтетический пациент.
4. Улучши 10–15 формулировок ответов через локальные шаблоны без запуска LLM: коротко, вежливо, одно уточнение за раз, не перечисляй 20 слотов голосом; максимум 3 ближайших релевантных варианта. Гарантируй выход по «оператор» и «начать заново» на каждом шаге.
5. В core/dialog.py проверь опасные ложные совпадения из HANDOFF (например «больница»). Вынеси правила в отдельный модуль, добавь tests/handoff_phrases.csv не менее 40 синтетических фраз с ожидаемыми решениями и автоматические тесты. Критичные формулировки должны срабатывать в тестовом наборе без пропусков. Медицинские консультации не производить.
6. Приоритет корректности данных выше «естественности»: Qwen/Ollama в этот этап НЕ ставь, если уже не установлено.
Этап C. Сразу после получения OpenAPI/Excel (самый высокий приоритет): реальная МИС
Это БЛОКЕР, поэтому не выдумывай реальные endpoints. Пока отсутствуют OpenAPI и Excel, подготовь расширяемый MIS-клиент и тесты на фиктивном HTTP-сервере; не пишите «live готово». После появления файлов:
1. Изучи фактический OpenAPI и файл Excel, создай docs/api-notes.md: base URL, маршруты, авторизация, поля, статусы, идентификаторы, реальные ответы на запросы, правила лимита и доступность чтения после записи. Не копируй токен.
2. Реализуй RealMIS без изменения интерфейса BookingService.create сверх необходимого; при необходимости аккуратно расширь контракт после записи в docs/contracts.md. Отдельный MockMIS всегда должен оставаться доступен; режим MIS_MODE=live включать только явно и только после настройки URL/token через env. В UI живой и тестовый режимы должны отличаться явной надписью.
3. Реализуй один централизованный клиент HTTP с таймаутами, обработкой 400/401/403/404/409/429/5xx, Retry-After, без печати URL с токеном. Ограничитель: максимум 10/min суммарно, лучше 8/min запас. Для одного процесса можно один shared limiter; при нескольких процессах нужен общий лимитер (SQLite или иной) либо явно ограничь запуск одним процессом. Кэшируй справочники. Мутации только после подтверждения.
4. Прочитай Excel и адаптируй core/schedule.py под обнаруженную схему. Не очищай расписание/резервации действующей БД. Сопоставь локальные врачебные ID с ID стенда. Если API не хранит расписание/занятость, объединяй Excel-слоты с текущими записями МИС и локальными pending/confirmed/uncertain, не полагайся только на локальный уникальный индекс.
5. Перед POST: validate doctor active, patient identifier, слоты, дату в будущем, подтверждение пациента. При таймауте POST: uncertain, слот блокируется локально, оператор/сверка; не retry CREATE без документированной идемпотентности. При успехе сохраняй external appointment ID. При 409 статус rejected и альтернативы.
6. Добавь unit/HTTP-mock tests: success, 400, 401, 404, 409, 429, timeout POST→uncertain, повторный запрос на занятый слот, два параллельных запроса на один слот, счётчик запросов в минуту. Для настоящего стенда запрашивай подтверждение у пользователя на один синтетический create; затем проверь запись в админке/чтением API, если разрешено.
7. Критерий: одна запись создана на стенде, есть подтверждённый ID, она отображается в админке и недоступна для повторного выбора, а UI правильно отличает результат «создана» от «не удалось проверить».
